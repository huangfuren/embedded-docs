## 1.1 环境搭建：装什么、怎么验证装好了

**结论**：入门只需要两样——编译器工具链（GCC）+ 一个顺手的编辑器（VS Code）。IDE 全家桶不是必需品：先用命令行把"编译"这件事看清楚，图形化以后随时可上。

| 平台 | 装什么 | 验证命令 | 期望输出 |
|---|---|---|---|
| Windows | MinGW-w64（GCC 的 Windows 移植版） | `gcc --version` | gcc 版本信息一行 |
| Linux | 发行版包管理器装 `gcc` 与 `make` | `gcc --version && make --version` | 两行版本信息 |
| macOS | Xcode Command Line Tools | `clang --version` | Apple clang 版本行（用法与 gcc 兼容） |

装好的三个判定标志：`gcc --version` 有输出；`where gcc`（Windows）或 `which gcc`（Linux/macOS）能找到路径；环境变量 PATH 里包含工具链的 bin 目录。

⚠️ **工程目录用纯英文路径**（如 `C:\code\hello`）：中文路径在部分工具环节会静默出错，这个纪律在嵌入式开发中同样成立。

## 1.2 编译四阶段：从 hello.c 到可执行文件

**机制**：`gcc hello.c -o hello` 一条命令背后是四个阶段，每个阶段有独立产物——所有"为什么报错"的定位都靠它。

| 阶段 | 单步命令 | 输入→输出 | 干什么 |
|---|---|---|---|
| ① 预处理 | `gcc -E hello.c -o hello.i` | .c → .i | 展开 `#include`、替换 `#define` 宏、处理条件编译 |
| ② 编译 | `gcc -S hello.i -o hello.s` | .i → .s | 语法/类型分析，生成本机汇编代码 |
| ③ 汇编 | `gcc -c hello.s -o hello.o` | .s → .o | 汇编翻译成机器码目标文件 |
| ④ 链接 | `gcc hello.o -o hello` | .o → 可执行文件 | 合并目标文件与库（printf 的实现在库里） |

两个可以亲手验证的证据：打开 `hello.i` 搜 `printf`——stdio.h 的几百行声明全被拷进来了；打开 `hello.s`——这是本机汇编，暂时读不懂没关系，知道"C 在这一步变成了汇编"即可。目标文件与机器码的细节在「计算机体系结构」002 展开。

**为什么要背四阶段**：报错发生在哪个阶段，就说明问题出在那一层——预处理期报错查头文件路径与宏；编译期报错是语法/类型错；`undefined reference` 是链接期；四阶段给了排查问题一个坐标系。

## 1.3 程序结构与 main：C 程序的最小骨架

```c
#include <stdio.h>   /* 预处理指令：引入标准输入输出的声明 */

int main(void)       /* main：程序入口；int：返回值是整数 */
{
    printf("hello, embedded!\n");   /* \n 是换行符 */
    return 0;        /* 返回 0 表示程序正常结束 */
}
```

- `#include` 行属于预处理阶段（§1.2 ①），不是 C 语句，结尾没有分号。
- `main` 是程序入口，操作系统从这里开始执行；`void` 表示不接收命令行参数，带参版本 `int main(int argc, char *argv[])` 用到时再讲。
- `return 0` 的返回值给操作系统看：终端里 `echo $?`（Linux/macOS）或 `echo %ERRORLEVEL%`（Windows cmd）能看到这个 0——"程序退出码"是系统判断成败的约定，这条线在「操作系统原理」001 会接上。

**观察与判断**：程序正常跑完应打印一行 `hello, embedded!` 且退出码为 0；打印了但退出码非 0，说明 return 值被改过；没打印，回到 §1.4 查报错。

## 1.4 报错与警告：怎么读、怎么处理

**判定**：错误（error）= 构建失败，没有产物；警告（warning）= 编译器怀疑有问题但放行。**第一天就开 `-Wall`**，让警告全部现形：

```bash
gcc -Wall hello.c -o hello
```

| 报错样例 | 阶段 | 原因 | 修法 |
|---|---|---|---|
| `expected ';' before ...` | 编译期 | 上一行少了分号 | 看报错行的**上一行** |
| `No such file or directory` | 预处理期 | `#include` 的头文件找不到 | 查拼写与 `-I` 路径 |
| `undefined reference to 'prinft'` | 链接期 | 函数名打错或只声明没实现 | 对照头文件改拼写/补实现 |
| `undefined reference to 'main'` | 链接期 | main 拼写错了（如写成 mian） | 改回来 |
| 警告 `implicit declaration` | 编译期 | 用了没声明的函数 | 引入对应头文件 |

**边界与风险**：警告不是噪音——未初始化、类型不匹配这类警告在嵌入式里常是真 bug 的预告。进阶纪律：工程化时开 `-Werror`（警告当错误），练习阶段先 `-Wall` 养成"零警告"的习惯。

## 1.5 Makefile 初见：为什么需要它、最小可用版

**问题**：文件一多，`gcc main.c utils.c -o app` 手敲既长又漏。Make 按"目标—依赖—命令"自动构建：

```makefile
app: main.o utils.o
	gcc main.o utils.o -o app
main.o: main.c
	gcc -Wall -c main.c
utils.o: utils.c
	gcc -Wall -c utils.c
clean:
	rm -f *.o app
```

三条观察：① 命令行前是 **Tab** 不是空格（Make 最著名的坑，报错 `missing separator` 就是它）；② 只重编"改动过的"文件——Make 比较目标与依赖的时间戳做增量构建，工程大了省大量时间；③ 嵌入式工程本质也是 Makefile/CMake，只是工具链换成交叉版（§1.6）。CMake 是"生成 Makefile 的工具"，入门先看清原生 Make 的机制。

## 1.6 交叉编译点题：本机编译与给别的芯片编译

**概念**：在 x86 电脑上编译出 ARM 芯片能跑的程序 = 交叉编译。工具链换名字：`gcc` → `arm-none-eabi-gcc`，四阶段完全相同，只是②③两步产出的是 ARM 机器码而非 x86 机器码。

| | 本机编译 | 交叉编译 |
|---|---|---|
| 运行平台 | 编译用的这台机器 | 目标开发板（MCU/SoC） |
| 工具链 | gcc（本机前缀） | arm-none-eabi-gcc 等带前缀 |
| 产物能否在本机跑 | 能 | **不能**（指令集不同） |

本库现阶段全部用本机编译练手；交叉编译的完整实践（安装、链接脚本、烧录）在规划板块「005 MCU 与外设」展开。现在只需立住一句：**四阶段不变，变的是工具链前缀**。

## 1.7 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | `gcc: command not found` | PATH 没含工具链 bin 目录 | 安装时勾选加入 PATH，或手动补环境变量 |
| 2 | 双击 exe 黑窗一闪而过 | 程序结束窗口就关 | 在终端里运行，顺便看退出码 |
| 3 | 改了代码结果没变 | 编的是旧文件/忘了重新构建 | 看构建输出的文件名；make 干净重编 |
| 4 | `missing separator` | Makefile 命令行前用了空格 | 改成 Tab |
| 5 | 中文路径下编译行为怪异 | 工具链对非 ASCII 路径支持差 | 工程放纯英文路径（§1.1） |
| 6 | 链接错误 undefined reference | 只声明未实现，或库没链上 | 补实现；库函数查链接选项（如 -lm） |
