## 1.1 认识工具链：GCC 是编译器，VS Code 是编辑器

**分工先说清**（这是初学者最常混的一对概念）：

- **VS Code** = 编辑器：负责写代码、语法高亮、跳转提示。它**自己不会编译**——它的 C/C++ 扩展只是"调用一个已经装好的编译器"的胶水。
- **GCC** = 编译器：真正把 `hello.c` 翻译成 `hello.exe` 的是它。没有编译器，写一百行代码也只是文本文件。
- 一句话：**VS Code 是笔，GCC 是工厂**——笔写订单，工厂出货。

**本库实测环境的来源**：GCC 在 Windows 上常用两种获取渠道——微软系 MSVC（Visual Studio Build Tools）与 GCC 系 MinGW-w64。本库选 GCC（嵌入式世界事实标准，后面交叉编译也是它的家族），用便携包 **w64devkit**（解压即用、不动注册表）。你机器上若已有 `C:\w64devkit`（本机已解压），直接用；没有就按 §1.2 下载。

## 1.2 环境搭建跟做：确认 GCC、配 PATH、装 VS Code 扩展

**跟做步骤**（三条，逐条验证）：

1. **确认 GCC 能被找到**：打开 VS Code → 菜单 Terminal → New Terminal（打开集成终端），输入：

   ```bash
   gcc --version
   ```

   预期输出（本机实录）：

   ```text
   gcc.exe (GCC) 16.2.0
   ```

   若提示"无法将 gcc 识别为命令"，说明 PATH 里还没有编译器目录——做第 2 步。
2. **把 GCC 加入 PATH**（一次性）：Windows 设置 → 搜索"编辑系统环境变量" → 环境变量 → 用户变量的 `Path` → 新建 → 填 `C:\w64devkit\bin` → 确定。**关掉所有终端窗口重开**（PATH 只在新终端生效），再跑一次 `gcc --version` 验证。
3. **装 VS Code 的 C/C++ 扩展**：左侧扩展图标（或 Ctrl+Shift+X）→ 搜索 `C/C++` → 安装微软官方的 **C/C++（ms-vscode.cpptools）**。它提供语法提示、跳转、调试，编译仍由 GCC 完成。

**试一试**：`gcc -v` 会打印更详细的版本与配置信息（比 `--version` 长得多）——编译器把"自己怎么被构建的"都告诉你了，这是查环境问题的入口。

## 1.3 第一个程序：hello.c 全流程

**跟做步骤**（每步都有预期结果）：

1. 建工程目录：资源管理器建 `C:\code\hello`（⚠️ **纯英文路径**——中文路径在部分工具环节会静默出错，这条纪律全库通用）。
2. VS Code → File → Open Folder → 打开 `C:\code\hello`。
3. 新建文件 `hello.c`，输入以下**完整内容**（这就是第一个完整示例）：

   ```c
   #include <stdio.h>     /* 预处理指令：引入标准输入输出的声明 */

   int main(void)         /* main：程序入口；int：返回值是整数 */
   {
       printf("hello, embedded!\n");   /* \n 是换行符 */
       return 0;          /* 返回 0 表示程序正常结束 */
   }
   ```

4. 在集成终端里编译并运行（一条命令完成四阶段，下一节拆开看）：

   ```bash
   gcc -Wall hello.c -o hello.exe
   .\hello.exe
   ```

   预期输出（本机实录）：

   ```text
   hello, embedded!
   ```

5. 看退出码——`main` 的返回值交给了操作系统：

   ```bash
   echo $LASTEXITCODE
   ```

   预期输出（PowerShell 集成终端实录）：

   ```text
   0
   ```

   Git Bash 里则是 `echo $?`，同一个东西。

**试一试**：① 把 `return 0;` 改成 `return 42;`，重编译运行再看退出码——变成 42；② 把字符串改成 `"hello, %d!\n"` 再编译——编译直接报错，这就是 §1.5 要学的读报错。

## 1.4 编译四阶段：亲眼看一遍

**机制**：`gcc hello.c -o hello.exe` 一条命令背后是四条流水线，每阶段有独立产物——**报错发生在哪个阶段，就说明问题出在哪一层**。

| 阶段 | 单步命令 | 输入→输出 | 干什么 |
|---|---|---|---|
| ① 预处理 | `gcc -E hello.c -o hello.i` | .c → .i | 展开 `#include`、替换宏 |
| ② 编译 | `gcc -S hello.i -o hello.s` | .i → .s | 语法分析，生成本机汇编 |
| ③ 汇编 | `gcc -c hello.s -o hello.o` | .s → .o | 汇编翻译成机器码目标文件 |
| ④ 链接 | `gcc hello.o -o hello.exe` | .o → exe | 合并目标文件与库（printf 的实现在库里） |

**跟做步骤**（在 hello 目录逐条执行，看产物）：

1. `gcc -E hello.c -o hello.i` → 打开 `hello.i`：本机实测 **1041 行**——stdio.h 的几百行声明全被拷了进来；文件末尾才是你的代码：

   ```c
   {
       printf("hello, embedded!\n");
       return 0;
   }
   ```

2. `gcc -S hello.i -o hello.s` → 打开 `hello.s`：C 变成了汇编（本机实录开头几行）：

   ```asm
   	.file	"hello.c"
   	.text
   	.section .rdata,"dr"
   .LC0:
   	.ascii "hello, embedded!\0"
   	.text
   	.globl	main
   main:
   	pushq	%rbp
   	movq	%rsp, %rbp
   ```

   暂时读不懂没关系——记住两句：`pushq %rbp` 是函数开场的固定动作，`.ascii "hello, embedded!\0"` 是你的字符串（注意编译器自动补了 `\0` 结尾，这条线索在「C语言」003 §3.3 收）。
3. `gcc -c hello.s -o hello.o` → 打开 `hello.o` 会发现是乱码——它已经是**机器码**了。用十六进制看开头（`xxd hello.o`，本机实录）：

   ```text
   00000000: 6486 0700 0000 0000 f001 0000 1400 0000  d...............
   ```

4. `gcc hello.o -o hello.exe` → 运行 `.\hello.exe` → `hello, embedded!`。

**试一试**：① `grep -c main hello.i` 数一下 main 出现次数；② 把 `gcc -E` 换成去掉 `#include` 行的源文件再跑，看 hello.i 行数从 1041 掉到几行——头文件展开就是行数爆炸的来源。

## 1.5 报错与警告：故意弄错三次

**判定**：error = 构建失败没产物；warning = 编译器怀疑但放行。**第一天就带 `-Wall`**。报错的格式是 `文件:行号:列: 类型: 内容`——三段式定位法。

**错误一：缺分号**（`bug1.c`，完整示例）：

```c
#include <stdio.h>
int main(void){
    printf("a\n")
    return 0;
}
```

编译 `gcc -Wall bug1.c -o bug1.exe`，本机实录报错：

```text
bug1.c:3:18: error: expected ';' before 'return'
    3 |     printf("a\n")
      |                  ^
      |                  ;
```

**读法**：错误说"在 return 之前期望分号"，但**问题在第 3 行行尾**——编译器在"下一行开头"才发现不对。规律：报错指向的行号常常是**出错行的下一行**。

**错误二：函数名打错**（`bug2.c`）：

```c
#include <stdio.h>
int main(void){prinft("a\n");return 0;}
```

编译（不带 -Wall）本机实录：

```text
bug2.c:2:16: error: implicit declaration of function 'prinft'; did you mean 'printf'?
```

这发生在**链接期**（prinft 没有实现可链）——好消息是新版 GCC 直接猜到了你想写 printf。规律：`undefined reference / implicit declaration` 都是"名字对不上"家族。

**错误三：警告的价值**——把 `printf("a\n")` 后面**加上分号但删掉 `#include`**，再开 `-Wall` 编译：隐式声明的警告会现形。警告不是噪音：未初始化、类型不匹配的警告在嵌入式里常是真 bug。**试一试**：自己造一个"缺右括号"的错误，观察报错行号和真实出错行的关系。

## 1.6 Makefile 初见：三文件工程与增量构建

**问题**：文件一多，`gcc main.c utils.c -o app.exe` 手敲既长又漏。Make 按"目标—依赖—命令"自动构建，**只重编改动过的文件**。

**完整示例**（4 个文件，建在 `C:\code\hello\mkdemo`）：

```c
/* main.c */
#include <stdio.h>
#include "utils.h"
int main(void)
{
    printf("2+3=%d\n", add(2, 3));
    return 0;
}
```

```c
/* utils.c */
int add(int a, int b){ return a + b; }
```

```c
/* utils.h —— 声明给别人看 */
int add(int a, int b);
```

```makefile
# Makefile —— 注意命令行前是 Tab，不是空格
app: main.o utils.o
	gcc main.o utils.o -o app.exe
main.o: main.c utils.h
	gcc -c main.c
utils.o: utils.c
	gcc -c utils.c
clean:
	del main.o utils.o app.exe
```

**跟做步骤**：① 四个文件建好后终端运行 `make`——本机实录：

```text
gcc -c main.c
gcc -c utils.c
gcc main.o utils.o -o app.exe
```

运行 `.\app.exe` → 输出 `2+3=5`。② 用 VS Code 修改 `utils.c`（比如加一行注释）再 `make`——本机实录：

```text
gcc -c utils.c
gcc main.o utils.o -o app.exe
```

**只重编了改动的 utils.c**（main.o 没动）——这就是增量构建，工程大了省大量时间。

**试一试**：把 Makefile 里 Tab 换成空格再 make——本机实录报错：

```text
bad.mk:2: *** missing separator (did you mean TAB instead of 8 spaces?).  Stop.
```

GNU make 连"你是不是把 Tab 打成空格"都提示了——这是 Makefile 头号坑。

## 1.7 交叉编译点题：给别的芯片编译

**概念**：在 x86 电脑上编译出 ARM 芯片能跑的程序 = 交叉编译。工具链换前缀：`gcc` → `arm-none-eabi-gcc`，四阶段完全相同，只是②③产出 ARM 机器码。**四阶段不变，变的是工具链前缀**——这句现在背下来，规划板块「005 MCU 与外设」实操时你会在自己的开发板上重走一遍本册的每一步。

## 1.8 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | "VS Code 编译不了" | 把编辑器当编译器 | 装编译器（GCC/MSVC）+ 扩展只是胶水（§1.1） |
| 2 | `gcc` 不是命令 | PATH 没含工具链 bin | §1.2 第 2 步；配完重开终端 |
| 3 | 双击 exe 黑窗闪退 | 程序结束窗口即关 | 集成终端里运行，顺便看退出码 |
| 4 | 改了代码结果没变 | 忘了重编/编错文件 | 看编译输出里的文件名 |
| 5 | `missing separator` | Makefile 用了空格 | 命令行前改 Tab（§1.6） |
| 6 | 中文路径下行为怪异 | 工具链对非 ASCII 支持差 | 工程放纯英文路径 |
| 7 | 报错行号指的位置不对 | 报错常指"出错行的下一行" | 往上看一行（§1.5） |
