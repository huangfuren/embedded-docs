## 322.1 线程是进程内的执行流 ★

**定义**：**线程**是进程**内部**的执行流。一个进程至少有一个线程（主线程）；同一进程的多个线程**共享该进程的地址空间**，各自只拥有独立的**栈**和**寄存器现场**。

**为什么要多线程**：一个进程要同时做几件事——界面要响应点击、后台要下载、定时要刷新。若只有一个执行流，下载时界面就卡住（因为它在等 IO，整个进程阻塞）。多线程让"等 IO 的那个"阻塞时，别的还能跑。

**"执行流"三个字要落到实处**：CPU 真正执行的是线程，不是进程。调度器调度的对象是线程（虽然口语常说"调度进程"）；PCB 之上还有 TCB（线程控制块），记录每个线程的栈指针与寄存器现场。**进程是资源容器，线程是执行单位**——这句话是整册的纲。

## 322.2 共享什么、独有什么 ★

![程序、进程与线程：一个文件，两次运行，三条执行流](../images/322-01-程序进程线程.svg)

**这张对照表要背下来**：

| 资源 | 进程之间 | 同一进程的线程之间 |
|---|---|---|
| 地址空间 | 独立（各自一套虚拟地址） | **共享** |
| 全局变量 / 堆 | 各自独立 | **共享**（改动彼此可见） |
| 栈 | 各自独立 | **各自独立**（每线程一个栈） |
| 寄存器现场 | 各自独立 | **各自独立** |
| 打开的文件 | 各自独立（默认） | **共享**（同一张文件表） |
| 创建/切换开销 | 大（换地址空间、刷 TLB） | 小（只换执行流） |
| 一个崩了的影响 | 不影响别人 | **整个进程一起死** |

**两个推论**：

1. **线程间传数据不需要 IPC**——直接读写同一个全局变量就行。这是线程最大的甜头，也是 323 一切事故的源头：**没有隔离，就没有免费的同步**。
2. **线程栈不能共享**——每个线程有自己的栈，所以"把局部变量地址传给另一个线程用"是悬空指针的经典来源（「C 语言」123 函数返回局部变量地址同理）。

**为什么一个线程崩全进程死**：地址空间是共享的，一个线程的野指针能踩坏另一个线程的栈、堆、甚至程序代码；操作系统无从判断"这块内存本来归谁"——它只看到"这个进程非法访问"，于是整个进程被终止。

## 322.3 多进程还是多线程：一对反向指标 ★

**决策表**：

| 你的诉求 | 选多进程 | 选多线程 |
|---|---|---|
| 稳定性优先（一个模块崩不能拖垮全部） | ✓ | ✗ |
| 大量数据要频繁交换 | ✗（要走 IPC） | ✓ |
| 需要跨机器扩展 | ✓ | ✗ |
| 创建/切换开销要小 | ✗ | ✓ |
| 各模块能用不同权限运行 | ✓ | ✗ |
| 开发调试成本要低 | ✓（隔离，问题局部） | ✗（竞态难复现） |

**一句话取舍**：**要隔离选多进程，要轻快共享数据选多线程**。实际工程里最常见的是混合：主进程用多进程分模块（浏览器一个标签页一个进程），进程内部再用线程池处理并发任务。

**为什么浏览器用多进程**：一个标签页的渲染代码崩了，不能把整个浏览器带走，也不能让它读到别的标签页的密码框内容——隔离性比开销更重要。反过来，一个视频解码器内部用多线程，是因为帧数据要在几个阶段间高速传递，走 IPC 的成本无法接受。

**误判提醒**：不要因为"线程更轻"就默认选线程。**轻的是创建开销，重的是一旦出竞态的调试成本**（323 §323.1 会看到，竞态在小数据量下可能"看起来是对的"）。

## 322.4 进程间通信（IPC）五机制 ○

**前提**：进程地址空间互相隔离（321 §321.3），所以数据交换必须走内核提供的正式通道——**内核当中转站**。

| 机制 | 形态 | 适合 | 代价 |
|---|---|---|---|
| 管道 / 命名管道 | 字节流，单向（匿名管道） | 父子进程、命令行 `\|` | 只能单向，容量有限 |
| 消息队列 | 离散消息，内核中转 | 结构化命令传递 | 两次拷贝（用户→内核→用户） |
| 共享内存 | 同一块物理页映射到两方地址空间 | 大数据量、最快 | 要自己配锁（回到 323 的问题） |
| 信号 | 异步通知，不带数据 | 控制：终止/挂起/超时 | 信息量极小，易丢 |
| Socket | 跨机器也能通 | 网络服务、本机进程通信 | 协议栈开销，本机可用 Unix 域套接字减负 |

**选择口诀**：**数据量小、要结构化 → 消息队列；数据量大、能自己管同步 → 共享内存 + 锁；只是通知 → 信号；要跨机器 → Socket；父子进程一次性传 → 管道**。

**与线程的对比**：线程间共享变量是"零成本"的（直接读写），IPC 全都至少有一次内核拷贝。这就是 322.3 里"大量数据频繁交换选线程"的量化依据。

## 322.5 实验：用管道把两个进程接起来 ○

**命题**：命令行里的 `|` 就是一个真实的 IPC 通道——左边进程的输出流进右边进程的输入，两个独立进程通过内核交接数据。

**完整示例（跟做）**：

```powershell
tasklist | findstr /i notepad
```

**读法**：`tasklist`（进程 A）把整张进程表写进标准输出；`|` 让内核把这份输出接到 `findstr`（进程 B）的标准输入；`findstr` 过滤后写到终端。**两个进程的地址空间毫不相干，数据全靠管道搬运**。

**验证隔离（跟做）**：把管道换成文件，效果一样但多了磁盘中转：

```powershell
tasklist > out.txt
findstr /i notepad out.txt
```

两次结果相同，但路径不同——**一次经过内核缓冲区（管道），一次经过文件系统**。这也是"管道比临时文件快"的原因：少了一次落盘。

**Linux 侧等价**：`ps -ef | grep notepad`；`ps -ef > out.txt && grep notepad out.txt`。**POSIX 管道是一条单向字节流**，父子进程方向可双向开两条。

**FreeRTOS 对照**：任务间用**队列**（传数据）与**信号量**（传状态），思想与消息队列/信号同源，形态更轻（没有内核/用户态之分，全在一个地址空间）。细节归规划「700 RTOS」。

## 322.6 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | 线程开满核数反而更慢 | 上下文切换与锁竞争 | 任务数 ≈ 核数附近，先测再调 |
| 2 | 一个线程崩，整个程序没了 | 共享地址空间 | 接受它，或改多进程（322.2） |
| 3 | 把局部变量地址交给别的线程 | 线程栈各自独立且会失效 | 用堆或加锁的共享结构（322.2） |
| 4 | 用全局变量在进程间传数据 | 地址空间隔离，根本看不到 | 走 IPC（322.4） |
| 5 | 共享内存用了但没加锁 | 内核不管同步 | 自己配锁，见 323 |
| 6 | 认为管道比文件快是"实现更好的缘故" | 少一次落盘 | 机制差异，不是优化（322.5） |
