## 332.1 调度器要同时满足五件事，而它们互相打架 ★

**定义**：**调度器**是内核里决定"就绪队列中谁上 CPU"的模块（311 §311.2 的进程管理，细化到"怎么选"）。它的输入是就绪队列，输出是下一个运行者。

**五个目标**（记住它们会互相打架，这是本册最重要的一句话）：

| 目标 | 含义 | 与谁冲突 |
|---|---|---|
| CPU 利用率 | 别让 CPU 空转 | 与响应时间冲突（频繁切换浪费） |
| 吞吐量 | 单位时间完成的任务数 | 与公平性冲突（偏爱短任务） |
| 周转时间 | 从提交到完成的总时长 | 与响应时间冲突（批处理思路） |
| 响应时间 | 从就绪到第一次被调度 | 与吞吐冲突（交互优先） |
| 确定性 | 最坏情况下多久一定响应 | 与吞吐/公平都冲突（实时任务要绝对优先） |

**为什么没有"最优调度"**：任何算法都在这些目标之间取一个点。批处理系统偏吞吐（少切换），桌面系统偏响应（多切换），RTOS 偏确定性（优先级绝对优先、可以饿死低优先级任务）。**看到"某调度算法很先进"的宣传，先问它牺牲了什么**。

**两条通用旋钮**：

- **时间片长度**——短则响应快、切换多；长则切换省、响应慢。桌面常见量级是几毫秒到几十毫秒。
- **优先级**——高优先级先跑；没有老化机制时，低优先级可能**永远等不到**（饿死）。

## 332.2 四种经典算法与它们各自牺牲了什么 ★

**用同一组任务推演**（不用跑程序，纸面算即可）：三个任务同时到达，运行时间 A=8、B=4、C=2（单位：时间片）。

| 算法 | 规则 | 执行顺序 | 平均等待 | 牺牲了什么 |
|---|---|---|---|---|
| FCFS 先来先服务 | 按到达顺序，谁先来谁先跑完 | A → B → C | (0+8+12)/3 = **6.67** | 短任务被长任务堵住（**护航效应**） |
| SJF 最短作业优先 | 每次选运行时间最短的 | C → B → A | (0+2+6)/3 = **2.67** | 需预知运行时间（现实中做不到）；长任务可能饿死 |
| RR 时间片轮转 | 每个任务跑一个时间片就换 | 片长 2：A B C A B A A | (6+6+4)/3 = **5.33** | 切换开销；片长难定 |
| 优先级 | 高优先级先跑 | 取决于优先级设定 | 取决于设定 | 低优先级饿死（需老化） |

**逐条读法**：

- **FCFS 的等待时间最差**，而且差得有规律：**前面堵一个长任务，后面所有短任务一起被拖**。这就是"护航效应"（convoy effect）——一批短任务排在一个长任务后面，像被护航一样慢。
- **SJF 的平均等待最短**，但它要预知未来（每个任务要跑多久）。现实中用"预测下一次运行时间"近似，或者干脆用多级反馈队列动态逼近。
- **RR 兼顾响应**：没有一个任务需要等别人跑完，最多等"前面每个任务各跑一个片"。代价是切换次数大增（331 §331.4 的开销）。
- **优先级最简单也最危险**：设错一个优先级，低优先级任务可以永远不跑。

**现代系统的实际做法是"组合"**：

| 系统 | 做法 |
|---|---|
| Linux（CFS） | 不用固定时间片，按"虚拟运行时间"排序，谁欠得少谁跑；交互任务自动获得更高权重 |
| Windows | 优先级驱动 + 时间片；前台进程获得优先级提升 |
| FreeRTOS | 严格优先级抢占，同优先级可配时间片轮转（`configUSE_TIME_SLICING`） |

**判断句**：**通用 OS 在"公平"和"响应"之间调参，RTOS 直接放弃公平、只保确定性**。这个分野决定了后面所有差异。

## 332.3 优先级反转：实时系统最隐蔽的故障 ○

**场景推演**（三个任务，优先级 高 > 中 > 低）：

| 时刻 | 发生什么 | 结果 |
|---|---|---|
| t1 | 低优先级任务拿到共享锁 | 正常 |
| t2 | 高优先级任务就绪，抢占，也要这把锁 | 高优先级**阻塞**等锁 |
| t3 | 中优先级任务就绪 | 中优先级**抢占了持有锁的低优先级任务** |
| t4 | 低优先级跑不了 → 锁不释放 → 高优先级一直等 | **高优先级被中优先级间接阻塞** |

**问题本质**：不是"高优先级被低优先级阻塞"（拿锁导致的短暂阻塞是正常的），而是**中间优先级插队，把短暂阻塞放大成了无限长**。优先级顺序在这里被彻底打乱——**低优先级的临界区，成了高优先级的瓶颈**。

**两个解法**：

| 解法 | 做法 | 代价 |
|---|---|---|
| 优先级继承 | 低优先级持锁期间，临时提升到等待者的优先级 | 实现复杂度；释放锁后要还原 |
| 优先级天花板 | 锁的优先级设为"所有可能用它的任务中的最高" | 需要静态分析，配置僵化 |

**历史教训**：1997 年火星探路者号在着陆前反复重启，最终定位就是优先级反转（一个低优先级的气象任务持锁，中优先级的通信任务插队，导致高优先级的总线管理任务拿不到锁，看门狗超时复位）。**这不是理论玩具，是让探测器差点失联的真实事故**。

**工程纪律**：实时系统里，**持锁的临界区越短越好**（323 §323.3 的纪律在这里多了一层含义），并且**高优先级任务用的锁，必须纳入优先级继承或天花板的保护**。

## 332.4 RTOS 的抢占式调度：确定性从哪来 ○

**定义**：**抢占式调度** = 高优先级任务一就绪，立刻打断正在跑的低优先级任务。**非抢占式**（协作式）= 当前任务主动让出才切换。

| | 抢占式 | 非抢占式 |
|---|---|---|
| 响应时间 | 可计算的最坏值（这是 RTOS 的立身之本） | 取决于最长任务何时让出 |
| 实现复杂度 | 高（任何时刻都可能切换） | 低 |
| 共享数据保护 | 必须用锁/关中断 | 天然少一类竞态 |
| 典型 | FreeRTOS（`configUSE_PREEMPTION = 1`）、绝大多数 RTOS | 早期协作式调度、部分简单固件 |

**确定性从哪来**——四个可测量的量，加起来就是最坏响应时间的骨架：

| 组成 | 含义 |
|---|---|
| 中断延迟 | 中断发生到 ISR 第一条指令执行（受关中断窗口影响，331 §331.2） |
| ISR 执行时间 | ISR 本身多长（所以必须快进快出） |
| 调度器决策时间 | 从"决定换"到"换完"的固定开销 |
| 阻塞时间 | 等锁、等资源的最长时间（受优先级继承影响，332.3） |

**关键认识**：RTOS 的"实时"不是"快"，而是**这四项有上界、可以算出来**。一个 50 MHz 的 MCU 跑得慢，但如果最坏响应是 40 微秒且从不超过，它就能满足 50 微秒的硬实时要求；一个 3 GHz 的 CPU 平均响应 5 微秒但偶尔抖到 500 微秒，就满足不了。

**配置上的三个真实旋钮**（FreeRTOS 为例）：`configUSE_PREEMPTION`（是否抢占）、`configMAX_PRIORITIES`（优先级档数，档数越多 RAM 开销越大）、`configUSE_TIME_SLICING`（同优先级是否轮转）。**档数不是越多越好**——每个优先级一个就绪链表，都占 RAM。

## 332.5 观察：优先级在系统里长什么样 ○

**目标**：把"优先级"从抽象概念变成屏幕上能看到的一列数字。

**跟做（Windows）**：任务管理器 → "详细信息"标签 → 右键列头 → 勾选"基本优先级"。你会看到一列数字（典型值 8 = Normal，10 = AboveNormal，13 = High，24 = Realtime）。

**等价命令（PowerShell）**：

```powershell
Get-Process -Name msedge,notepad -ErrorAction SilentlyContinue |
    Select-Object Name, PriorityClass, Id
```

**你会看到什么（本机实测，不是固定输出）**：能读到的进程会显示 `Normal` / `AboveNormal` 之类的类别名；**相当一部分系统进程会返回"拒绝访问"**——读其他进程的优先级本身需要权限。

**这个"拒绝访问"值得停一下**：它不是命令写错了，而是权限体系的正常表现——**优先级是内核管理的敏感属性，普通用户无权窥探别人的**。这与 313 §313.1 的特权级是同一条线的两端：看得见什么、改得动什么，都由权限决定。

**Linux 侧等价**：`ps -eo pid,ni,pri,comm | head`（`NI` 是 nice 值 −20~19，越小优先级越高；`PRI` 是内核换算后的优先级）；`nice -n 10 ./prog` 以更低优先级启动，`renice` 调整运行中的进程。

**观察任务（不给答案，自己判断）**：找两个你自己启动的程序，比较它们的优先级类别；再想一下——**为什么前台窗口的程序往往比后台的高一档？**

## 332.6 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | 低优先级任务永远不跑 | 没有老化机制，被高优先级持续抢占 | 加老化、或提高其优先级（332.1） |
| 2 | 高优先级任务莫名超时 | 优先级反转（332.3） | 优先级继承 / 天花板 |
| 3 | 任务明明是实时优先级却响应不及时 | ISR 太长或关中断太久 | 查中断延迟与 ISR 时长（332.4） |
| 4 | 认为 RTOS 比 Linux 快 | 混淆"快"与"确定" | 比的是最坏响应上界（332.4） |
| 5 | 优先级档数开到最大 | 每个档占一份就绪链表内存 | 够用即可，嵌入式 RAM 贵 |
| 6 | 时间片调到极小想"更公平" | 切换开销吃掉吞吐 | 先测再调，别凭感觉（331 §331.4） |
