## 212.1 IEEE 754：三个字段装下一个实数（实验：ieee754.c 拆位） ★

**问题**：整数只要"位模式 ↔ 值"一一对应就行；实数有无穷多个、还有小数部分，32 位怎么装？

**答案**：不装精确值，装**科学计数法的三个零件**——`值 = 符号 × (1 + 尾数) × 2^指数`。

| 字段 | 位数（float / double） | 装什么 | 偏移量 |
|---|---|---|---|
| **符号** sign | 1 / 1 | 正 0 负 1 | — |
| **指数** exponent | 8 / 11 | 二进制指数 + 偏移 | 127 / 1023 |
| **尾数** fraction | 23 / 52 | 小数点后的有效位（隐含前导 1） | — |

**两个必须知道的约定**：① 指数存的是**加过偏移**的值（float 存 `index + 127`），这样指数不用单独存符号位；② 规格化数的尾数**隐含一个前导 1**（即实际有效位是 24 位），所以 23 位尾数能表示 24 位精度。

### 完整示例（[code/212/ieee754.c](../code/212/ieee754.c)——把 32 位拆开看）

```c
static void dump(float f)
{
    uint32_t u;
    memcpy(&u, &f, sizeof u);            /* 按位复制，不改变位模式 */
    unsigned sign = (u >> 31) & 1u;
    unsigned expo = (u >> 23) & 0xFFu;
    unsigned frac = u & 0x7FFFFFu;
    printf("%-14.9g sign=%u exp=0x%02X(%4d) frac=0x%06X bits=0x%08X\n",
           (double)f, sign, expo, (int)expo - 127, frac, u);
}
```

**跟做步骤**：`cd code/212` → `gcc -Wall ieee754.c -o ieee754.exe -lm` → `.\ieee754.exe`（`-lm` 是因为用了 `fabs`）。**预期输出（本机实录，第 1 段）**：

```text
1              sign=0 exp=0x7F(   0) frac=0x000000 bits=0x3F800000
-2.5           sign=1 exp=0x80(   1) frac=0x200000 bits=0xC0200000
0.100000001    sign=0 exp=0x7B(  -4) frac=0x4CCCCD bits=0x3DCCCCCD
1e+10          sign=0 exp=0xA0(  33) frac=0x1502F9 bits=0x501502F9
3.40282347e+38 sign=0 exp=0xFE( 127) frac=0x7FFFFF bits=0x7F7FFFFF
```

**四处必看**：

1. **`1.0f` 是 `0x3F800000`** —— 指数 `0x7F` = 127，减偏移得 0，尾数全 0。也就是 `1.0 × 2⁰`。这个位模式会被反复用作"1.0 的身份证"。
2. **`-2.5f` 符号位是 1，指数是 1，尾数 `0x200000`** —— 2.5 = 1.25 × 2¹，尾数 0.25 对应 `0100…`，左对齐进 23 位就是 `0x200000`。**符号位只占 1 位，改它只翻转正负，别的位一律不动**。
3. **`0.1f` 的位模式是 `0x3DCCCCCD`** —— 尾数 `0x4CCCCD` 是个无限循环小数的截断（0.1 的二进制是 `0.0001100110011…` 循环）。**这是 0.1 存不准的根源**，不是 bug，是 2 进制表示不了 1/10。
4. **`FLT_MAX` 附近指数是 `0xFE`（127）** —— 最大指数留给 `inf` 与 `NaN`，所以有限数的指数上限是 127（对应 2¹²⁷）。

**试一试**：在 `dump()` 后面加一行 `dump(0.5f)` 和 `dump(4.0f)`，观察指数怎么变——0.5 的指数是 -1（`0x7E`），4.0 的指数是 2（`0x81`），尾数都是 0。**只有尾数非零的数才"不整齐"**。

## 212.2 精度的代价：0.1 存不准、2²⁴ 之后整数丢（实验：三种比较结果） ★

**两条精度边界**，缺一条都会写错判断：

| 边界 | 数字 | 含义 |
|---|---|---|
| 小数精度 | 约 7 位十进制有效数字 | 第 8 位开始不可信，`0.1` 存成 `0.100000001` |
| 整数精度 | **2²⁴ = 16777216** | 超过它，相邻可表示整数的间隔 > 1，`+1` 可能无效 |

**为什么是 2²⁴**：尾数 23 位 + 隐含前导 1 = 24 位有效位。24 位能精确表示 `0 ~ 2²⁴` 的所有整数；再大，间隔就变成 2、4、8……

### 完整示例（同 `ieee754.c` 第 2、3 段）

```c
float  f  = 0.1f;
double d  = 0.1;
printf("float  0.1 = %.20g\n", (double)f);
printf("double 0.1 = %.20g\n", d);
printf("0.1f + 0.2f == 0.3f ? %d\n", (0.1f + 0.2f) == 0.3f);
printf("fabs(0.1f+0.2f-0.3f) = %.10e\n", fabs((double)(0.1f + 0.2f) - 0.3));

float big = 16777216.0f;                 /* 2^24 */
printf("2^24 + 1 == 2^24 ? %d\n", (big + 1.0f) == big);
printf("(float)16777217 = %.1f\n", (double)(float)16777217);
```

**预期输出（本机实录，第 2、3 段）**：

```text
== 2) 0.1 到底存成了什么 ==
float  0.1 = 0.10000000149011611938
double 0.1 = 0.10000000000000000555
0.1f + 0.2f == 0.3f ? 1
fabs(0.1f+0.2f-0.3f) = 1.1920928966e-08

== 3) 单精度的整数天花板 2^24 ==
2^24            = 16777216.0
2^24 + 1 == 2^24 ? 1
(float)16777217 = 16777216.0
2^23 + 1 == 2^23 + 2 ? 0  (2^23 附近最小间隔是 1)
```

**五处必看（第 3 处是全场最反直觉的）**：

1. **`float 0.1` 的真实值是 `0.100000001490116…`** —— 不是"差不多 0.1"，是"差了 1.5e-9"。`double` 好一些但同样不准（`0.10000000000000000555`）。**没有任何一个浮点类型能精确存 0.1**。
2. **`0.1f + 0.2f == 0.3f` 打印 `1`（相等）** —— 这和教科书上"0.1+0.2 != 0.3"的结论相反。原因是 **float 精度低，两边都舍入到同一个位模式**，误差被更大的舍入吃掉了。**"相等"是巧合，不是正确**。
3. **换成 double 比较，差值是 `1.192e-08`** —— 同一组数字，精度一变，结论就变。这条是本册最该记住的：**浮点的比较结果依赖精度，不能用"等不等"来判对错**。
4. **`2²⁴ + 1 == 2²⁴` 打印 `1`（成立）** —— 16777217 存不进 float，被舍入回 16777216。`(float)16777217` 直接打印 `16777216.0`，眼见为实。
5. **`2²³ + 1` 与 `2²³ + 2` 仍然不等（打印 0）** —— 2²³ 附近间隔还是 1，所以 +1 有效。**精度边界不是"到了 2²³ 就突然变粗"，是随指数逐级变粗**。

**结论三条**：① 小数用 `fabs(a-b) < eps` 比较，`eps` 按量级取（C 153 §153.3 给过写法）；② 需要精确十进制（金额、计量）用**整数 + 定标**，别用浮点；③ 判断"两个浮点是否相等"前先问"我到底要多精确"。

**试一试**：① 把 `2^24` 那段改成 `1e8f`（一亿），再打印 `1e8f + 1.0f == 1e8f`——依然成立，而且间隔已经到 8；② 把 `0.1f + 0.2f == 0.3f` 的 `f` 后缀全去掉（用 double），看结果从 `1` 变成 `0`。

## 212.3 浮点的字节序：跨平台传 float 为什么更容易错 ○

**规则本身不新鲜**：多字节数据在内存里的排列有大端小端之分，`bswap` 转换（C 143 §143.3）。浮点特殊在**你不知道该按几个字节换**——`float` 是 4 字节、`double` 是 8 字节，而协议里常只写"float"两个字。

### 完整示例（同 `ieee754.c` 第 4 段）

```c
float one = 1.0f;                        /* 位模式 0x3F800000 */
unsigned char *p = (unsigned char *)&one;
printf("1.0f 的 4 个字节自低地址起: %02X %02X %02X %02X\n", p[0], p[1], p[2], p[3]);
```

**预期输出（本机实录）**：

```text
1.0f 的 4 个字节自低地址起: 00 00 80 3F
（小端：低字节在前；若为 3F 80 00 00 则是大端）
```

**三处必看**：

1. **`00 00 80 3F` 是本机（小端）的排列** —— 位模式 `0x3F800000` 被反着放进内存。**字节序只影响内存排列，不影响数值**：读回来还是 1.0。
2. **只换 4 个字节里的前两个，会得到一个"合法但不是 1.0"的浮点** —— 整数换了字节序通常是荒谬的大数，一眼能看出错；浮点换了字节序可能仍是**一个正常的数**（比如 `0x0000803F` ≈ 4.6e-41），悄无声息地算错。这是浮点字节序比整数危险的地方。
3. **协议里必须写清三件事**：字节数（4 / 8）、字节序（大端 / 小端）、格式（IEEE 754 单 / 双）。少写一条，跨平台就要出错——网络协议普遍规定"大端 + IEEE 754"，就是为了消掉这个歧义。

**试一试**：把 `1.0f` 换成 `1.0`（double，8 字节），打印 8 个字节。你会发现前 4 个字节全是 `00`——**同一个"1.0"，float 和 double 的字节序列完全不同**，这就是协议里必须写明宽度原因。

## 212.4 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | 用 `==` 判两个浮点相等，偶尔对偶尔错 | 舍入误差，且随精度变化（§212.2 第 2、3 处） | `fabs(a-b) < eps` |
| 2 | 金额算着算着差一分钱 | 十进制小数在二进制里存不准 | 整数分 / 定点数 |
| 3 | 大整数赋给 float 后变了 | 超过 2²⁴，间隔 > 1 | 用 double 或 int64 |
| 4 | 循环 `for (float f = 0; f != 1; f += 0.1)` 死循环 | 累加误差让 `f` 永远碰不到 1 | 用整数计数，或 `f < 1.0f` |
| 5 | 跨平台收到的 float 是个怪数 | 字节序不同，但仍是"合法浮点" | 协议固定大端 + 明确宽度 |
| 6 | `float` 与 `double` 混算结果跳变 | 隐式提升 + 双重舍入 | 全程统一 double，或显式转换 |
