## 231.1 四级存储阶梯：寄存器、SRAM、Flash、外扩 ★

MCU 里没有"存储金字塔"这种教科书图，只有四种速度差别很大的介质：

| 层级 | 典型访问周期 | MCU 上的对应 | 你能决定的 |
|---|---|---|---|
| 寄存器 | 1 | CPU 内部 R0~R15 | 编译器的分配（`-O` 等级影响） |
| 片内 SRAM | 1~2（通常 0 等待） | 变量、栈、堆 | **可以**：把热点函数/数据搬进来 |
| 片内 Flash | 1 + 等待周期 | 程序、`const` 常量表 | 部分可以：`__ramfunc` 搬函数 |
| 外扩 SRAM / SDRAM | 数周期到数十周期 | 大容量缓冲 | 尽可能少碰，或用 DMA 成批搬 |

**关键差别**：SRAM 访问通常**固定周期**，Flash 访问**随主频变化**——这是下一节的全部内容。

**为什么变量不在 Flash 里**：Flash 是只读通道（哈佛结构，见 221 §221.1），变量要能改，必须住 SRAM。这也解释了启动代码为什么要搬 `.data`：初值在 Flash，运行要可写，所以复制一份到 SRAM。

> **与 500 板块分界**：SRAM 单元（6T）与 Flash 单元（浮栅）在电路层怎么工作，见 500 数字电路 533 的存储器部分。本册只讲"速度差怎么影响你的代码"。

### 完整示例（[code/231/mem_step.c](../code/231/mem_step.c)——工作集逐档放大）

本机测不了 MCU 的等待周期，但能测同一件事的另一种形态：**工作集越大，单次访问越慢**——这条规律在 PC 的缓存和 MCU 的存储阶梯上是同一个道理。

```c
/* 随机访问（破坏预取），工作集从 4 KB 逐档放大到 128 MB */
for (int k = 0; k < n; k++) {
    size_t lines = sizes[k] / LINE;
    shuffle(idx, lines);                      /* 打乱访问顺序 */
    double t0 = now_s();
    for (unsigned i = 0; i < HOPS; i++)       /* 每档固定 100 万次 */
        sink += (unsigned char)buf[idx[i & (lines - 1)] * LINE];
    double t1 = now_s();
}
```

**跟做步骤**：`cd code/231` → `gcc -O0 -Wall mem_step.c -o mem_step.exe` → `.\mem_step.exe`

**预期输出（本机实录，一次完整运行）**：

```text
工作集        单次访问
------------  ----------
      4 KB       0.9 ns
     64 KB       1.0 ns
    512 KB       1.1 ns
   4096 KB       3.0 ns
  32768 KB      17.6 ns
 131072 KB      17.2 ns

校验和 sink = 990000000
(随机访问；顺序访问时预取器会把差异抹平)
```

**三处必看**：

1. **512 KB 以内约 1 ns** —— 工作集还在片上缓存里，几乎零等待。
2. **4 MB 变成 3 ns** —— 开始装不下，访问要跨到下一层。
3. **32 MB 以上约 17 ns** —— 彻底落到内存，比第一档慢近 20 倍。

另两次运行数值有浮动（32 MB 档落在 13~18 ns 之间），**看趋势不看绝对值**——这一点在 MCU 上同样成立：手册给的等待周期是典型值，实际还受总线仲裁与温度影响。

**试一试**：把 `shuffle` 换掉（让 `idx[i] = i`，即顺序访问）再跑——台阶会明显变平，因为预取器提前把后面的行搬进缓存了。这解释了为什么"遍历数组"比"随机跳着访问"快得多。

## 231.2 Flash 等待周期：主频的隐形税（`FLASH_ACR`） ★

**问题从哪来**：Flash 的读取速度有物理上限（通常几十 MHz）。CPU 主频一旦超过它，就必须在每次取指时**插入等待周期**（wait state），否则读到的数据不可靠。

**以 STM32F103（Cortex-M3）为例**（数据手册公开规格，具体查你的型号）：

| 系统时钟 | 需要的等待周期 |
|---|---|
| 0 ~ 24 MHz | 0 |
| 24 ~ 48 MHz | 1 |
| 48 ~ 72 MHz | 2 |

这些配置写在 `FLASH_ACR` 寄存器的 `LATENCY` 位里，**必须在提升主频之前配好**，否则芯片跑飞。这也是 `SystemInit()` 里那几行"看不懂的寄存器赋值"在干的事。

**等待周期的代价**：一条从 Flash 取指的指令，原本 1 周期，现在要 3 周期（72 MHz 下）。**平均 CPI 上升，实际算力达不到标称主频。**

**芯片厂商的三层缓解**（按代价从低到高）：

| 手段 | 原理 | 效果 |
|---|---|---|
| 预取缓冲区（prefetch buffer） | 一次多读几条指令存起来，顺序执行时命中 | 顺序代码几乎无感，跳转多的代码效果差 |
| 指令 cache / ART Accelerator | 缓存最近用过的指令行 | 循环体效果好 |
| **把代码搬进 RAM** | 彻底绕开 Flash | 有效，但吃 SRAM |

## 231.3 把代码放进 RAM：`__ramfunc` 与什么时候值得 ★

**做法**：给函数加段属性，让链接器把它放进 RAM，启动代码再从 Flash 搬一次（和 `.data` 一个道理）：

```c
/* GCC / ARM GCC：链接脚本里要有 .ramfunc 段的搬运规则 */
__attribute__((section(".ramfunc")))
void critical_isr_body(void)
{
    /* 需要确定性时序的代码 */
}

/* Keil MDK：__ramfunc 关键字 + 分散加载文件配置 */
__ramfunc void critical_isr_body(void) { /* ... */ }
```

**什么时候值得**（三条判据，满足两条以上再搬）：

1. **时序确定性要求高**：比如软件模拟的协议时序、精确到周期的位操作。
2. **函数被高频调用**：每次都吃等待周期，累计起来才明显。
3. **SRAM 有余量**：搬代码是拿 RAM 换速度，SRAM 紧张的芯片搬不起。

**不值得的情况**：主循环里跑一次的初始化代码、很少进的分支——搬了只是浪费 SRAM。

## 231.4 DMA：绕过 CPU 的搬运工，以及 cache 一致性的坑 ★

**没有 DMA 时**：串口收 1 KB 数据 → 每来一个字节触发一次中断 → CPU 进 ISR 把字节读进缓冲区。1000 次中断，每次十几个周期的响应延迟 + 现场保存，CPU 大部分时间在做搬运。

**有 DMA 时**：CPU 只发一次配置（源地址、目的地址、长度），DMA 控制器自己搬完，**只在"全部搬完"时中断一次**。

| | 中断逐次搬 | DMA 成批搬 |
|---|---|---|
| CPU 参与次数 | 每字节一次 | 整块一次 |
| 中断次数 | 1000 | 1 |
| 适用 | 低速、少量、需要逐字节处理 | 高速、大块、纯搬运 |

**代价一：争总线**。DMA 与 CPU 共用内存总线，大块搬运会挤占 CPU 的访问带宽，表现为"开了 DMA 之后主循环反而变慢一点"。

**代价二：cache 一致性**（只在有 D-Cache 的芯片上出现，见 §231.5）。DMA 直接写内存，CPU 的 cache 里可能还是旧值。必须在使用前做 invalidate：

```c
/* Cortex-M7 + CMSIS：DMA 写入完成后，让 CPU 丢掉这段的 cache */
SCB_InvalidateDCache_by_Addr((uint32_t *)buf, len);
```

**忘记这一步的现象**：DMA 明明搬完了、标志位也置了，读出来的还是全 0 或旧数据——这类 bug 极难查，因为逻辑上完全正确。

## 231.5 Cortex-M7 的 I/D-Cache：为什么换芯片突然变快 ○

**分水岭**：Cortex-M3 / M4 **没有 cache**，每次取指都要过 Flash（带等待周期）；Cortex-M7 有 **I-Cache（指令）与 D-Cache（数据）**，常用代码和数据驻留在 cache 里，不再每次都去 Flash/SRAM 取。

**典型现象**：同一份工程从 M4 移植到 M7，**主循环快了 2~3 倍**——不是代码变好了，是 cache 把 Flash 等待周期挡在了外面。

**代价**：所有"外设直接访问内存"的场景都要考虑一致性——DMA、以太网描述符、USB 缓冲区。规则很简单：**凡是 DMA 碰过的内存，CPU 使用前必须 invalidate，CPU 写完交给 DMA 前必须 clean**。

```c
SCB_CleanDCache_by_Addr((uint32_t *)tx_buf, len);  /* CPU 写完 → 交给 DMA 前 */
SCB_InvalidateDCache_by_Addr((uint32_t *)rx_buf, len); /* DMA 写完 → CPU 读前 */
```

**排查口诀**：M7 上"逻辑没问题但数据不对"，先怀疑 cache。

## 231.6 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | 提高主频后程序跑飞 | `FLASH_ACR` 的等待周期没同步调高 | 先配 LATENCY 再切 PLL，顺序不能反 |
| 2 | 标称 72 MHz 但实测算力明显不足 | Flash 等待周期让平均 CPI 变高 | 关键代码放 RAM，或依赖 ART/Cache |
| 3 | 大数组放函数里栈溢出 | 栈在 SRAM 且通常只有 KB 级 | 改静态/全局，或缩小尺寸 |
| 4 | 开了 DMA 主循环反而变慢 | DMA 与 CPU 争总线带宽 | 分批搬，避免长时间独占 |
| 5 | DMA 搬完但读出来全是旧值 | D-Cache 里有旧副本（M7） | 读前 `SCB_InvalidateDCache_by_Addr` |
| 6 | 换到 M7 后某个外设数据错乱 | cache 一致性没处理 | 同上，clean/invalidate 成对使用 |
| 7 | 掉电后变量值全丢 | 住在易失存储（SRAM） | 要保存的显式写 Flash/EEPROM（有擦写寿命） |
| 8 | 频繁写 Flash 把芯片写坏 | Flash 有擦写次数上限（万次量级） | 数据先留 RAM，低频落盘，或做磨损均衡 |
