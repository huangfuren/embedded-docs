## 143.1 对齐两准则与 offsetof ★

**定义**：**对齐**是编译器把每个成员放到"自己宽度的整数倍"地址上的规则，中间补的空隙叫 **padding**。132 §132.1 给过结论（`struct A` 12 字节、重排成 8），本节把它变成**可计算、可测量**的两条准则：

| # | 准则 | 用来算 |
|---|---|---|
| 1 | 每个成员的**偏移量**是其**自身大小**的整数倍 | 成员住在第几字节 |
| 2 | 结构体**总大小**是**最大成员大小**的整数倍 | 末尾补几个字节 |

**完整示例**（[code/143/layout.c](../code/143/layout.c)）——四组对照一次量完：

```c
#include <stdio.h>
#include <stddef.h>

struct A { char c; int i; char c2; };
struct B { int i; char c; char c2; };

#pragma pack(push, 4)
struct P4 { int a; double d; char c; };
#pragma pack(pop)
struct N  { int a; double d; char c; };

#pragma pack(push, 1)
struct P1 { char c; int i; char c2; };
#pragma pack(pop)

int main(void)
{
    printf("A: c@%zu i@%zu c2@%zu sizeof=%zu\n",
           offsetof(struct A, c), offsetof(struct A, i), offsetof(struct A, c2), sizeof(struct A));
    printf("B: i@%zu c@%zu c2@%zu sizeof=%zu\n",
           offsetof(struct B, i), offsetof(struct B, c), offsetof(struct B, c2), sizeof(struct B));
    printf("N (natural): sizeof=%zu\n", sizeof(struct N));
    printf("P4 (pack 4): sizeof=%zu\n", sizeof(struct P4));
    printf("P1 (pack 1): sizeof=%zu\n", sizeof(struct P1));
    return 0;
}
```

**跟做**：`cd code/143` → `gcc -Wall layout.c -o layoutdemo.exe` → `.\layoutdemo.exe`。**预期输出（本机实录）**：

```text
A: c@0 i@4 c2@8 sizeof=12
B: i@0 c@4 c2@5 sizeof=8
N (natural): sizeof=24
P4 (pack 4): sizeof=16
P1 (pack 1): sizeof=6
```

**三处必看的机制**：① **准则 1 的直接证据**：`struct A` 里 `char c` 占 0、`int i` **不能**放 1（1 不是 4 的倍数），于是跳到 **4**，`c2` 跟在 8——中间 1~3 是 padding；② **同样的成员换个顺序（struct B），偏移变成 0/4/5，总大小从 12 降到 8**——`c` 与 `c2` 挤在一起，只在末尾补到 8（准则 2：最大成员 int 是 4，8 是 4 的倍数）——**成员顺序就是内存布局，重排是白捡的优化**；③ `offsetof(类型, 成员)`（`<stddef.h>`）直接给出偏移量，比手工 `(char*)&a.i - (char*)&a` 干净——**它是唯一能在编译期算偏移的标准工具**。

**`struct N` 为什么是 24**：成员 `int a`(4)、`double d`(8)、`char c`(1)，最大成员 8 字节 → `a` 占 0~3、`d` 必须是 8 的倍数所以跳到 8~15、`c` 占 16，末尾补到 8 的倍数 → **24**。按"1+4+1=6"算的人会差出 18 字节。

**纸上算法**（三步，任何时候都能用）：

1. 从偏移 0 开始，逐个成员：偏移 = 向上取整到"该成员大小的倍数"；
2. 全部放完后，总大小向上取整到"最大成员大小的倍数"；
3. 中间跳过的字节数就是 padding，末尾补的就是尾部 padding。

**试一试**：① 给 `struct A` 加一个 `double d;` 放到最后，用三步法先算 sizeof 再跑程序对账（提示：最大成员变 8）；② 把 `struct B` 的成员改成 `char c; char c2; int i;`——sizeof 是多少？先算再验。

## 143.2 `#pragma pack`：压不压的对账 ○

**定义**：`#pragma pack(n)` 把对齐基数从"成员自身大小"压到"成员大小与 n 中的较小者"，从而**消掉 padding**。它是**编译器指令不是 C 语句**，只影响它作用范围内的结构体。

**实测对账**（同一份 `layout.c` 的三行输出）：

| 写法 | sizeof | 说明 |
|---|---|---|
| `struct N`（自然对齐） | **24** | `int` + `double` + `char`，8 字节对齐 |
| `struct P4`（`pack(4)`） | **16** | 对齐基数压到 4，`double` 只能按 4 对齐 |
| `struct P1`（`pack(1)`） | **6** | 完全紧贴，padding 归零 |

**为什么 `pack(4)` 是 16 不是 24**：`a` 占 0~3、`d` 按 4 对齐所以能从 **4** 开始（占 4~11）、`c` 占 12，总大小向上取整到 4 的倍数 → **16**。**"压到 4"不是"压到 1"**——它只是让 8 字节成员不再强求 8 的倍数。

**该压与不该压**（这条判断比语法重要）：

| 场景 | 压不压 | 理由 |
|---|---|---|
| 解析通信报文（Modbus、自定义二进制协议） | ✅ `pack(1)` | 协议规定的字节位置不能有 padding，否则整包错位 |
| 映射硬件寄存器块 | ✅ `pack(1)` 或逐字段偏移 | 寄存器地址是芯片手册钉死的 |
| 存 Flash / EEPROM 的结构 | ✅ `pack(1)` | 存储布局要与读取方一致，且省空间 |
| 程序内部的数据结构 | ❌ 不压 | 压了会让成员跨地址边界，**访问变慢甚至在某些架构上触发异常**（ARM 某些模式下非对齐访问会 fault） |

**三处必看的机制**：① **`pack(1)` 的代价是访问性能**——成员可能落在非自然边界上，CPU 需要两次访存拼一个值；x86 能忍，ARM 要看配置；② **`push/pop` 要成对**：`#pragma pack(push, 1)` ... `#pragma pack(pop)` 恢复原设置，只写 push 不写 pop 会污染后面所有结构体；③ **`pack` 不是标准 C**，是编译器扩展——GCC/Clang/MSVC 都支持同一写法，但**不写 pack 时的默认对齐各家可能不同**（这就是"同一份代码换个编译器大小变了"的原因）。

**试一试**：① 把 `P4` 的 `pack(push, 4)` 改成 `pack(push, 8)` 再跑，看它回到 24（与 `N` 相同）——证明"基数不小于最大成员时等价于不压"；② 把 `P1` 外面那对 `push/pop` 删掉，只留 `#pragma pack(1)`，然后**在后面再加一个** `struct Q { char c; int i; };`，看它是否也被压成 5——这就是"忘了 pop"的污染。

## 143.3 字节序：小端、大端与探测 ★

**定义**：多字节数据在内存里，**低字节放低地址**叫**小端**（little-endian，x86/ARM 默认），**高字节放低地址**叫**大端**（big-endian，多数网络协议与部分嵌入式芯片）。132 §132.2 的 union 实拍已经给过一次证据（`0x12345678` 读成 `78 56 34 12`），本节把它做成**可判定、可翻转**的工具。

**完整示例**（[code/143/endian.c](../code/143/endian.c)）——探测、翻转、双重翻转：

```c
#include <stdio.h>
#include <stdint.h>

static int is_little_endian(void)
{
    uint16_t v = 0x0102;
    return *(uint8_t *)&v == 0x02;
}

static uint32_t bswap32(uint32_t x)
{
    return ((x & 0x000000FFu) << 24) | ((x & 0x0000FF00u) << 8) |
           ((x & 0x00FF0000u) >> 8)  | ((x & 0xFF000000u) >> 24);
}

int main(void)
{
    printf("little endian? %d\n", is_little_endian());

    uint32_t host = 0x12345678;
    printf("host   = 0x%08X\n", host);
    printf("bswap  = 0x%08X\n", bswap32(host));
    printf("bswap2 = 0x%08X\n", bswap32(bswap32(host)));

    uint8_t *b = (uint8_t *)&host;
    printf("bytes: %02X %02X %02X %02X\n", b[0], b[1], b[2], b[3]);
    return 0;
}
```

**跟做**：`gcc -Wall endian.c -o endiandemo.exe` → `.\endiandemo.exe`。**预期输出（本机实录）**：

```text
little endian? 1
host   = 0x12345678
bswap  = 0x78563412
bswap2 = 0x12345678
bytes: 78 56 34 12
```

**三处必看的机制**：① **探测函数的原理**：把 `0x0102` 存进 2 字节变量，看**低地址那一格**是 `0x02` 还是 `0x01`——是 `0x02` 就是小端（低字节在低地址）。这个函数只有三行，却是所有跨平台库的第一道门；② **`bytes: 78 56 34 12`** 与 `host = 0x12345678` 是同一份数据的两种视图——**内存里就是反的，只有按 `%X` 读出来才是正序**；③ **`bswap` 两次回到原值**——翻转是可逆对合，所以"发之前翻一次、收之后翻一次"就能跨字节序通信。

**大端与小端的对照**（同样存 `0x12345678`）：

| 地址 | 小端（x86/ARM） | 大端（网络序） |
|---|---|---|
| +0（低地址） | `78` | `12` |
| +1 | `56` | `34` |
| +2 | `34` | `56` |
| +3（高地址） | `12` | `78` |

**网络标准是**大端****——所以套接字编程有一组 `htons/htonl/ntohs/ntohl`（host to network short/long），它们的实现就是"小端机器上翻一次，大端机器上什么都不做"。

**试一试**：① 把 `is_little_endian` 改成返回 `*(uint8_t*)&v == 0x01` 再跑，看结果变成 0（这就是大端判定）——体会"判据只有一个字节的差别"；② 用 `union { uint32_t i; uint8_t b[4]; }` 重写 §143.3 的字节打印（132 §132.2 的写法），确认两种手段给出同一组字节。

## 143.4 跨平台报文的布局纪律 ★

**定义**：报文的**字节位置是协议规定的**，而 C 结构体的 padding 与字节序**都不是协议规定的**——所以"把收到的字节直接强转成结构体指针"这件事，在跨平台场景里几乎是必翻车的写法。

**错误示范**（不要这样写）：

```c
/* 假设收到一包 6 字节报文，协议规定：1 字节类型 + 4 字节数值 + 1 字节校验 */
struct Msg { uint8_t type; uint32_t value; uint8_t crc; };   /* 自然对齐下 sizeof 可能是 12！ */
void on_recv(uint8_t *buf, int len)
{
    struct Msg *m = (struct Msg *)buf;   /* 雷：padding 与字节序都不匹配 */
    printf("value = %u\n", m->value);    /* 读到的可能是错位的垃圾 */
}
```

**三处问题**：① `sizeof(struct Msg)` 在自然对齐下是 **12**（`value` 会被对到偏移 4），而报文只有 6 字节——**多读 6 个字节的越界**；② 即使加了 `pack(1)` 让布局对上，`m->value` 仍是**按本机字节序**解释的，而协议规定的是大端；③ `buf` 可能**不是 4 字节对齐的地址**，`m->value` 这种访问在 ARM 上可能直接 fault。

**正确做法**（三条，按重要性排）：

| # | 纪律 | 做法 |
|---|---|---|
| 1 | **逐字节解析，不强转** | 用移位拼装：`value = (buf[1]<<24)|(buf[2]<<16)|(buf[3]<<8)|buf[4];` |
| 2 | **用定宽类型** | `uint8_t` / `uint32_t` 而不是 `int`、`long`（宽度随平台变） |
| 3 | **显式定字节序** | 协议定大端就按大端拼（如上）；要本机序再用 `bswap`（§143.3） |

**发出去的对称写法**：

```c
/* 把 value 按大端写进 buf[1..4] */
buf[1] = (uint8_t)(value >> 24);
buf[2] = (uint8_t)(value >> 16);
buf[3] = (uint8_t)(value >> 8);
buf[4] = (uint8_t)(value);
```

**为什么逐字节拼装是"笨但正确"**：它不依赖对齐、不依赖字节序、不依赖 `sizeof`——**三个跨平台变量全部被消掉**。代码多写四行，换来的是在任何机器上行为一致。

**什么时候可以直接强转**：**同一台机器、同一个编译器、同一份定义**的内部数据（比如你自己在内存里传结构体），这时候布局天然一致，强转没问题。**一旦数据要出门（走网络、进 Flash、跨进程共享内存），就必须按上面三条来**。

**试一试**：① 把错误示范里的 `struct Msg` 跑一次 `sizeof` 与 `offsetof`，量出它真实的 12 字节与 `value@4`——亲眼看到"多读 6 字节"；② 写一对 `pack_msg` / `unpack_msg` 函数（按大端拼/拆 `uint32_t`），往返一次验证值不变——这是所有协议栈的最小单元。

## 143.5 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | struct 大小比成员之和大 | 对齐 padding（A=12 实录） | 按"从大到小"重排；先纸上算三步（§143.1） |
| 2 | 换个编译器 sizeof 变了 | 默认对齐基数与 ABI 相关 | 关键结构体显式 `pack`；别依赖默认值（§143.2） |
| 3 | 加了 `pack(1)` 后某些平台崩 | 成员非对齐访问触发异常 | 只在报文/存储结构上用；访问时复制到对齐变量再读（§143.2） |
| 4 | 忘了 `pack(pop)`，后面的结构体全变小 | pack 设置是"直到 pop"的全局状态 | 成对 `push/pop`（§143.2 试一试 ②） |
| 5 | 跨机器读到的多字节值"反了" | 字节序不同（小端 vs 大端） | 协议定死字节序；收发各翻一次（§143.3） |
| 6 | 直接强转收到的报文，值错位 | padding + 字节序 + 对齐三重不匹配 | 逐字节解析 + 定宽类型（§143.4） |
| 7 | 报文解析偶发崩溃 | 缓冲区地址非 4 字节对齐，强行按 int 访问 | 逐字节拼装，或 `memcpy` 到局部变量（§143.4） |
| 8 | `int` 在板子上是 2 字节 | 嵌入式平台 int 宽度可能不是 4 | 一律用 `stdint.h` 的 `int32_t` 等定宽类型（121 §121.1） |
