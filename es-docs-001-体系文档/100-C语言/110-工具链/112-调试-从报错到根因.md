## 112.1 两类问题：编不过 与 编过跑不对 ★

**定义**：调试的第一刀不是"看代码"，而是**分类**。C 的问题只有两大类，但它们的证据来源完全不同：

| 类别 | 判据 | 证据在哪 | 去哪一册 |
|---|---|---|---|
| **编译期错** | `gcc` 不给产物 | 编译器打印的 `文件:行:列: 类型:` 三段式 | 111 §111.6 |
| **运行期错** | 有产物，但输出/行为不对，或直接崩 | 程序自己的输出、退出码、调试器 | **本册** |

**为什么必须先分类**：拿 GDB 去查一个编译期错误是徒劳的——根本不存在可执行的程序；反过来，盯着报错文本找"为什么 sum 是 37808"也永远找不到，因为编译器压根没觉得有问题。

**运行期错再分三档**，处理成本依次下降、证据依次变硬：

| 档 | 表现 | 第一手段 |
|---|---|---|
| ① 崩溃 | 进程被信号杀死（段错误、除零） | GDB 栈回溯（§112.4） |
| ② 结果不对但不崩 | 算错、打印乱值、偶尔对 | 打点法（§112.2）+ GDB 看变量（§112.3） |
| ③ 偶发 | 跑十次错一次、换机器就变 | 优化等级对照（§112.5）+ 未定义行为排查 |

**本册的实验对象**（`buggy.c`，故意埋两个经典 bug）：

```c
#include <stdio.h>

int sum_to(int n)                 /* 求 1..n 之和 */
{
    int sum;                      /* bug 1：局部变量未初始化 */
    for (int i = 1; i <= n; i++)
        sum += i;
    return sum;
}

int main(void)
{
    int arr[5] = {1, 2, 3, 4, 5};
    int total = 0;
    for (int i = 0; i <= 5; i++)  /* bug 2：i<=5 越界读一位 */
        total += arr[i];
    printf("sum_to(100) = %d\n", sum_to(100));
    printf("total = %d\n", total);
    return 0;
}
```

**跟做**：`gcc -Wall buggy.c -o buggydemo.exe` → `.\buggydemo.exe`。**预期输出（本机实录）**：

```text
sum_to(100) = 37808
total = 15
```

**三处必看的机制**：① 编译**零警告**——`-Wall` 对这种形态（循环内累加标量）在本机 GCC 16.2.0 的 `-O0` 下保持沉默（实测；换形态不一定——131/123/142 的实录在 `-O0` 就报了，见 §112.5）；② `sum_to(100)` 应该是 **5050**，实得 37808——`sum` 是栈上残留的垃圾值，累加从垃圾开始；③ `total` 得 15 是对的，`arr[5]` 越界读到的恰好是 0——**越界没报错不代表没越界**，换个编译器、换行代码顺序，这个 0 就变成别的数（133 §133.3 有同类实证）。

**试一试**：把 `int sum;` 改成 `int sum = 0;` 再跑，`sum_to(100)` 立刻回到 5050——先验证你对 bug 1 的定位是对的，再学后面的工具。**这一步很重要：调试的前提是你先有一个能验证的假设。**

## 112.2 打点法：printf 是最便宜的调试器 ★

**定义**：打点法 = 在可疑位置插入输出，用"打印出来的中间值"对照"你以为的值"。它不需要额外工具、不改编译参数，是**最先该用**的手段——很多人跳过它直接上调试器，反而更慢。

**打点的四条纪律**（不做这四条，打点会变成噪声）：

| # | 纪律 | 反例 |
|---|---|---|
| 1 | 点打在**假设的分界**上，不是随便撒 | 每行都打，输出几百行没人看得完 |
| 2 | 一次只验证**一个**假设 | 同时改三处再跑，错了不知道是谁 |
| 3 | 打**输入和输出**，不打"我到这里了" | `printf("here\n")` 只证明执行过，不证明值对不对 |
| 4 | 收工**删点**（或用宏开关） | 留下的调试打印混进正式输出 |

**完整示例**（`probe.c`）——给 `sum_to` 加两个点，看 sum 从哪开始：

```c
#include <stdio.h>

int sum_to(int n)
{
    int sum;
    printf("[probe] enter sum_to, n=%d, sum(before)=%d\n", n, sum);  /* 点 1：入口 */
    for (int i = 1; i <= n; i++)
        sum += i;
    printf("[probe] leave sum_to, sum(after)=%d\n", sum);            /* 点 2：出口 */
    return sum;
}

int main(void)
{
    printf("sum_to(5) = %d\n", sum_to(5));
    return 0;
}
```

**跟做**：`gcc -Wall probe.c -o probedemo.exe` → `.\probedemo.exe`。**预期输出（本机实录）**：

```text
[probe] enter sum_to, n=5, sum(before)=32759
[probe] leave sum_to, sum(after)=32774
sum_to(5) = 32774
```

**读法**：`sum(before)=32759` 这一行就是根因——进入函数时 sum 已经不是 0，所以出口是 32774 而不是 15。**打点的价值在于把"猜"变成"看见"**：不用读汇编、不用懂栈布局，一行输出就把"未初始化"钉死了。

**注意一个陷阱**：读一个未初始化的变量本身也是未定义行为（编译器有权把它优化成任何值），所以打点看到的 32759 **只是这一次的结果**，下一台机器可能打 0、也可能打优化后的怪值。**打点能告诉你"它没被初始化"，但不能告诉你"它一定等于多少"。**

**试一试**：① 把点 1 挪到 `for` 循环**里面**（每轮打 i 和 sum），观察累加过程——这就是"逐轮对照"；② 用宏开关把打点变成可关闭的：`#define DBG 1` 配合 `#if DBG ... #endif`（宏与条件编译详见 124），收工时把 `DBG` 改 0，一个字符关掉所有点。

## 112.3 GDB 入门：断点、单步、看变量 ★

**定义**：GDB 是"让程序停下来给你看"的工具。它的三个动作对应三个问题——**break**（我要在哪停）、**next**（往下走一步）、**print**（这个变量现在是多少）。

**前提**：编译时加 `-g`，把"机器码 ↔ 源码行"的对照表写进产物。**不带 `-g` 就看不到行号和变量名**，这是新手第一堵墙。

**跟做步骤**（在 `buggy.c` 所在目录逐条执行）：

1. 带调试信息重编：

   ```bash
   gcc -Wall -g -O0 buggy.c -o buggydemo.exe
   ```

   `-O0` 关优化——优化会把变量塞进寄存器、把循环拆开重排，调试时看到的行号会"跳"。**调试一律先 `-O0`。**

2. 启动 GDB，在 `sum_to` 上打断点并运行：

   ```bash
   gdb ./buggydemo.exe
   ```

   进入交互后依次输入 `break sum_to`、`run`。**预期输出（本机实录，已略去沙箱环境的若干 hook 警告行）**：

   ```text
   Breakpoint 1 at 0x14000149b: file buggy.c, line 6.
   Thread 1 hit Breakpoint 1, sum_to (n=100) at buggy.c:6
   6	    for (int i = 1; i <= n; i++)
   ```

3. 看参数、往下走一步、再看变量：

   ```text
   (gdb) print n
   $1 = 100
   (gdb) next
   7	        sum += i;
   (gdb) next
   6	    for (int i = 1; i <= n; i++)
   (gdb) print sum
   $2 = 32759
   ```

   `$2 = 32759` 就是根因：**循环第一轮结束时 sum 已经是 32759**，说明它进函数时没被清零。

4. 看调用栈（谁把它叫来的）：

   ```text
   (gdb) bt
   #0  sum_to (n=100) at buggy.c:6
   #1  0x00007ff65330151f in main () at buggy.c:17
   ```

   `#0` 是当前帧、`#1` 是调用者——`main` 的第 17 行调了 `sum_to`。

5. 退出：`quit`。

**非交互写法**（把命令串起来，适合写进笔记或脚本）：

```bash
gdb -batch -ex "break sum_to" -ex "run" -ex "print n" -ex "next" -ex "print sum" -ex "bt" ./buggydemo.exe
```

**三处必看的机制**：① `break sum_to` 停在函数**第一行可执行语句**（不是 `{` 那一行）；② `next` 是"把本行执行完"，遇到函数调用**不进去**（想进去用 `step`）；③ `print` 支持表达式，`print sum + 1`、`print arr[5]` 都能算——查越界就靠 `print arr[5]` 直接看那个非法格子。

**试一试**：① 用 `break buggy.c:16` 在越界那一行下断点，`next` 到 i=5 时 `print i` 和 `print arr[i]`，亲眼看到它读到了数组外面；② 把 `next` 换成 `step` 走进 `printf` 内部，体会两者的区别（走进去会看到一堆库代码，这正是"不该进的地方"）；③ `print sizeof(arr)/sizeof(arr[0])` 应该得 5——顺手验证循环条件 `i<=5` 是错的。

## 112.4 段错误：三分钟定位到行 ★

**定义**：段错误（SIGSEGV）= 进程访问了无权访问的地址，硬件异常、内核终止进程。它的特征是**退出码 139**（128 + 信号号 11）。

**完整示例**（`crash.c`）——顺着空指针写：

```c
#include <stdio.h>

static void write_through(int *p)
{
    *p = 42;                      /* 顺着空指针写 */
}

int main(void)
{
    int *p = NULL;
    printf("about to crash\n");
    write_through(p);
    printf("never reached\n");
    return 0;
}
```

**跟做**：`gcc -Wall -g crash.c -o crashdemo.exe` → `.\crashdemo.exe`。**预期输出（本机实录）**：

```text
（什么都没有）
```

退出码 **139**（Git Bash 里 `echo $?` 可得；PowerShell 里 `$LASTEXITCODE` 得 3221225477，同一个信号）。

**第一个反直觉**：`printf("about to crash\n")` 明明在崩溃**之前**，为什么一个字都没打印？因为 stdout 是**行缓冲/全缓冲**，`\n` 只是把内容留在缓冲区里，还没落到终端——进程被信号杀掉时缓冲区跟着蒸发。**加一行 `fflush(stdout);` 就能看到它**（本机实录）：

```text
about to crash
```

接着照样段错误退出 139。这条实测直接推翻"printf 在崩溃前一定打出来了"的直觉——**崩溃现场的输出可能是残缺的，别用它判断执行到哪**。

**GDB 三分钟定位法**（不用断点，直接跑）：

```bash
gdb -batch -ex "run" -ex "bt" -ex "print p" ./crashdemo.exe
```

**预期输出（本机实录，已滤掉沙箱 hook 警告）**：

```text
Thread 1 received signal SIGSEGV, Segmentation fault.
0x00007ff617ba149c in write_through (p=0x0) at crash.c:5
5	    *p = 42;                      /* 顺着空指针写 */
#0  0x00007ff617ba149c in write_through (p=0x0) at crash.c:5
#1  0x00007ff617ba14d5 in main () at crash.c:12
$1 = (int *) 0x0
```

**读法**（三行读出全部信息）：

| 行 | 读到什么 |
|---|---|
| `in write_through (p=0x0) at crash.c:5` | **崩在哪一行**（crash.c:5），**当时的指针是 0** |
| `#0 ... write_through` | 出事的函数 |
| `#1 ... main () at crash.c:12` | **谁传了这个空指针**（main 的第 12 行） |

**没有调试器怎么办**：在可疑函数入口打一行 `printf("p=%p\n", (void*)p);`——打印出来的 `0000000000000000` 同样能定位到"谁传了空指针"。打点法和 GDB 不是二选一，**打点负责缩小范围，GDB 负责给出精确行号**。

**试一试**：① 把 `int *p = NULL;` 改成 `int *p = (int *)0x1234;`（一个没映射的地址）再跑——退出码还是 139，但 GDB 的 `print p` 变成 `0x1234`，体会"野指针"和"空指针"在证据上的差别；② 故意在 `write_through` 里加一句 `printf("p=%p\n", (void*)p);` 但不加 `fflush`，观察这行会不会打出来（多半不会——它也在缓冲区里）。

## 112.5 优化等级为什么让 bug 变脸 ★

**定义**：`-O0`（默认，不优化）与 `-O2`（常用优化）会让**同一份源码**产生不同的机器码。对于**行为有定义**的程序，两者结果必须一致；结果不一致，就说明程序里有**未定义行为**（UB，undefined behavior）——标准对它不规定任何结果，编译器随便怎样都合法。

**实证**（同一个 `buggy.c`，只换优化等级）：

| 编译命令 | 警告 | 运行结果 |
|---|---|---|
| `gcc -Wall buggy.c` | 无 | `sum_to(100) = 37808`、`total = 15` |
| `gcc -Wall -O2 buggy.c` | **两条警告** | `sum_to(100) = 5050`、`total = 15` |

**`-O2` 的警告原文（本机实录）**：

```text
buggy.c:16:21: warning: iteration 5 invokes undefined behavior [-Waggressive-loop-optimizations]
   16 |         total += arr[i];
buggy.c:7:13: warning: 'sum' may be used uninitialized [-Wmaybe-uninitialized]
    7 |         sum += i;
```

**三处必看的机制**：① **未初始化检查与优化等级：按形态记，别背绝对结论**——这类检查依赖数据流分析，覆盖随优化等级与代码形态变化。本库同机实测（GCC 16.2.0）：`buggy.c` 的"循环内累加标量"形态 `-O0` 不报、`-O2` 才报；"直接打印数组元素/读 malloc 块"的形态 `-O0` 就报（131/123/142 三册实录）。不变的是：`-Wall` 没警告 ≠ 没问题；② `-O2` 下 `sum_to(100)` 变回 5050，不是因为编译器"修好了 bug"，而是它分析了 UB 之后**假定 sum 从 0 开始**——**结果正确纯属巧合，换个场景就错**；③ 越界那条被识别成 `-Waggressive-loop-optimizations`，名字很吓人，本质是"你的循环在最后一步踩了 UB"。

**实践结论**（三条可执行的）：

1. **日常用 `gcc -Wall -Wextra -O2`**：优化能把 UB 从"跑出错值"提前成"编译警告"，这是免费的静态检查。
2. **调试时用 `-O0 -g`**：优化会重排、内联、消变量，行号对不上、`print` 说"optimized out"。
3. **两个等级都跑一遍**：结果不一样，程序里就有 UB——不用继续找"哪个结果是对的"，**两个都不算对**。

**试一试**：① 把 `int sum;` 改成 `int sum = 0;` 并修掉 `i <= 5`，再用 `-O0` 与 `-O2` 各跑一次，确认两者**完全一致**（有定义的程序的判据）；② 用 `gcc -Wall -O2 -fno-aggressive-loop-optimizations` 关掉那条优化再跑，看警告与结果怎么变——体会"编译器有权，但它也在替你探测"。

## 112.6 没有 ASan 时的替代纪律 ○

**问题**：越界读写最麻烦的一点是**多数时候不崩**（§112.1 的 `total = 15` 就是），而正规武器 AddressSanitizer 并非随处可用。

**本机实测**（w64devkit 不自带 ASan 运行库）：

```bash
gcc -fsanitize=address crash.c -o crashasan.exe
```

```text
C:/w64devkit/bin/ld.exe: cannot find -lasan: No such file or directory
collect2.exe: error: ld returned 1 exit status
```

链接期就失败——**这不是"用法错了"，是这套工具链没装这个库**。要 ASan 就得换完整 MSYS2 或 Linux 环境。

**没有 ASan 时的四道纪律**（本机同样能查出大部分越界）：

| # | 手段 | 做法 | 能抓什么 |
|---|---|---|---|
| 1 | **金丝雀值** | 在数组两端各留一个元素填固定标记（如 `0xDEADBEEF`），越界后会改掉标记 | 越界写 |
| 2 | **边界打印** | 循环前后打印 `sizeof arr / sizeof arr[0]` 与循环变量的首末值 | off-by-one |
| 3 | **编译期常量断言** | `_Static_assert(sizeof arr == 20, "size changed")` | 布局被意外改动 |
| 4 | **`-O2` 静态探测** | 见 §112.5，UB 在优化下更容易被警告出来 | 未初始化、越界常量下标 |

**完整示例**（`canary.c`）——用两个哨兵位抓越界写：

```c
#include <stdio.h>

int main(void)
{
    int box[7] = {0xDEADBEEF, 0, 0, 0, 0, 0, 0xDEADBEEF};  /* 两端各一个哨兵 */
    int *arr = &box[1];                                     /* 真正的 5 个格子 */
    const int len = 5;

    for (int i = 0; i <= len; i++)   /* 故意越界一位 */
        arr[i] = i * 10;

    printf("front canary = 0x%X %s\n", box[0],
           (unsigned)box[0] == 0xDEADBEEF ? "(intact)" : "(OVERWRITTEN!)");
    printf("back  canary = 0x%X %s\n", box[6],
           (unsigned)box[6] == 0xDEADBEEF ? "(intact)" : "(OVERWRITTEN!)");
    return 0;
}
```

**跟做**：`gcc -Wall canary.c -o canarydemo.exe` → `.\canarydemo.exe`。**预期输出（本机实录）**：

```text
front canary = 0xDEADBEEF (intact)
back  canary = 0x32 (OVERWRITTEN!)
```

**读法**：`back canary` 从 0xDEADBEEF 变成 **0x32**——正是 `arr[5] = 5 * 10 = 50 = 0x32` 写进去的值。越界写的是 `box[6]`（尾部哨兵所在），所以标记被覆盖；`front canary` 安然无恙，说明越界方向是往后。**这一步已经给出了两个信息：越界发生了、方向是向后**。剩下的"i 是几"用 §112.2 的打点法一轮就能看到。

**为什么这是"没有 ASan 也能查"**：ASan 靠编译器给每个对象插红区，金丝雀靠你自己摆哨兵——思路相同，只是手工版。代价是只能抓**你想到要摆哨兵的那几处**，所以它适合"怀疑某个数组被写坏了"的场景，不适合全自动巡检。

**试一试**：把循环条件改回 `i < len` 再跑，两个 canary 都应是 `(intact)`——先确认你的修复真的修好了，而不是碰巧。

## 112.7 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | 开了 `-Wall` 没警告，程序还是算错 | 未初始化检查的覆盖随优化等级与形态变化，`-O0` 常漏报 | 日常 `-Wall -Wextra -O2`（§112.5） |
| 2 | 段错误前一行 printf 没打出来 | stdout 缓冲未刷新就被信号杀死 | 崩溃排查前加 `fflush(stdout)`（§112.4） |
| 3 | GDB 里看不到变量名/行号 | 编译没加 `-g` | `gcc -g -O0`（§112.3） |
| 4 | GDB 里 `print` 说 optimized out | 开了优化，变量被塞进寄存器 | 调试用 `-O0`（§112.3） |
| 5 | `-O0` 对、`-O2` 错（或反过来） | 程序里有未定义行为 | 两个等级都跑，不一致就是 UB（§112.5） |
| 6 | 越界写一点报错都没有 | C 不做边界检查，踩到别的格子照常运行 | 金丝雀哨兵 + 边界打印（§112.6） |
| 7 | ASan 链接失败 `cannot find -lasan` | 工具链没装 ASan 运行库 | 换 MSYS2/Linux，或用 §112.6 的四道纪律 |
| 8 | 调试打印收工忘删，混进正式输出 | 打点没用开关 | 用 `#define DBG` + `#if` 控制（§112.2，宏见 124） |
